## Project
RulealizeStudio.Avalonia — a VS Code extension that makes an Avalonia application out of a rule set and XAML, and reads its test design on the application's own window.

The extension is `editor/vscode`, a TypeScript client of `src/RulealizeStudio.Server`. Beside it are the parts an application made of a rule set and XAML is built from — `src/RulealizeStudio.Binding`, `src/RulealizeStudio.Generator`, `src/RulealizeStudio.Hosting`, all `net10.0` with nullable and implicit usings — and two such applications, signup and countdown, in `sample/`. One headless xUnit suite in `test/` covers all of the .NET side.

It consumes `Rulealize` as a published package, the way any host does. No sibling repository is read or built.

## The division this program exists to keep
No rule set is named in the program, and no control is named in a rule set. What an application's screen does is an answer the runtime gave — `GetValidInputs`, `ValidInput.Open`, `OpenParameter.Description`, `InputRejectedException`, `GetOutcomes`, `Project` — and which control an answer becomes is decided in the application's XAML and nowhere else.

The first five are the same questions for every document. `Project` is the one that differs: a projection is whatever this rule set had further to say about a position, so an application binds its keys by name in its XAML, and nothing here names them.

A change that puts a rule set's identifier in this code, or a control's name in a document, is the change that ends the program's reason to exist.

## Where this is going
The arc ends with somebody who is not an engineer building an Avalonia application; for now an agent writes the rules, since nothing else lets such a person assemble them; that they do is aimed at, with no means of it in sight, and nothing here waits on it. All of it happens in VS Code, so that engineers, non-engineers and agents share one environment. The model an application binds is generated from its rule set — do not reopen that by binding into a dictionary somewhere.

## Shape
`Session` is the core and has no Avalonia in it: one rule set, one position, the positions it came from, what became of applying an input, and what the rule set says about where it is. It is testable without a window and is tested that way.

`Session` lives in `RulealizeStudio.Binding`, beside the layer an application binds to: `RuleModel` (change notification, back and forward, outcomes), `RuleInput` (a command enabled by `GetValidInputs`, a property per parameter, refusals as `INotifyDataErrorInfo`), `Limits` (an open parameter's bounds) and `Labels` (a label document: the sentence a refusal is said in, keyed by the name its clause has in a specification — the host's, since the runtime gives only a code; a parameter's `invalid` is a code of the same set, keyed the same way). Nothing there references Avalonia either.

`RulealizeStudio.Generator` reads an application's rule set at build time and writes the model its XAML binds to. It reads names and a field's schema and nothing else; a value only evaluation knows is `object`. Of a window's XAML it reads the one thing compiling it drops — its root's `x:DataType`, the model the window binds — and writes it into the assembly beside the file's name (`Window`), with a mark that it did, which is the generator's package's `.axaml` among its additional files. Beside the rule set it builds in every label document named after it, `signup.labels.en.json`, found by its name, so an application's csproj lists only its rule set. `Document` is the one place it maps a schema `op` to a type. `RulealizeStudio.Hosting` is what an application's `Main` calls, and opens every window compiled into the application's assembly, each on the model of the rule set it binds, one model per rule set (`RuleWindows`) — an application is as many windows, rule sets and specifications as it needs, none counted against another. When a window is shown is the rules' answer bound in its XAML, `RuleWindow.ShowWhen`, and its × is the move `RuleWindow.CloseWith` binds or closes nothing, so every way a window appears or goes is a move the test design walks; the application ends when none is shown. An assembly built before the generator recorded windows, with one model, has every window given that one. `Reach` there is how a control is found for a move — by the `RuleInput.Apply` its `Command` is, and its `CommandParameter`, a window's × by its `CloseWith` — on every window shown, so no control is named for a runner's sake. `Replay` is the runner: it reads a `ruledger/test-design/v2` file, the form Ruledger's CLI writes, and walks it on a window. A design reaches this repository as that file, committed beside its rule set — never derived while the suite runs, which would move the design with the rule set and fail nothing.

An application in `sample/` is a rule set, a `MainWindow.axaml`, a `Program.cs` that is one call, and a csproj that lists the vocabularies; beside the rule set may sit the test design `ruledger derive` wrote for it, the application's specification, `specification.json`, whose elements bind it to the rules, and its label documents — documents, not code. Adding anything else to one would make an application more than a rule set and XAML, and `ModelTests` fails on it. The same folder before any rule is written is what `rulealize-avalonia-app` in `Rulealize.Templates` makes, run by the extension's **New application**: its `Program.cs` names no model — `RuleApp` finds the one generated into the assembly, or opens the window with nothing bound — so it is never edited. Beside it the template writes `AGENTS.md` — what is in the folder, how each file is read, Rulealize's guides linked rather than restated, and what each tool does and reports, each the program the editor runs — with a `CLAUDE.md` that only reads it; it tells an agent nothing to do and no point at which it is finished, since that is whoever uses the agent's to decide and how such an application is worked on is Rule-Derived Test Design's to say. The samples carry none of it. An application reaches `Binding`, `Hosting` and `Generator` as packages, and the server as the local tool `rulealize-studio`, from `feed/` while they are not on nuget.org.

`RulealizeStudio.Server` is what the extension asks about a document: a language server on standard input and output that compiles a rule set (`Check`, which only turns the place the runtime named into a place in the text) against the vocabularies of the application's build output, which `Vocabularies` reads into memory rather than loading from their files — the server runs for as long as VS Code is open, and an assembly loaded from its path is held until the process ends, so the application could not be built again meanwhile — and reads again once that folder is built again. It also reads a screen: `Design` lists the names a window's XAML binds — what the rules behind it have to give — from the XAML alone, before any rule set exists, telling the rules' names from the model's own by the binding layer's members and matching a rule set's name by the generator's `Name`, which the server compiles in rather than restates. And it reads the specification: `Rules` names every rule of a rule set — a field, an input and each parameter, guard, actor, `validate` clause by its code and its effects, a definition, a projection, the ending — by a pointer whose parts are names and never a place in the text, and `Specification` reads every specification in the application's folder — `specification.json`, named after no rule set since it comes first, and any other JSON whose `$schema` says it is one —, in the format its `$schema` names: `StateMachine`, the one there is, whose states, transitions and notes each hold what they say and the rules they are bound to by those names, so no file binds it from outside. A second format is added there the same way, holding its own bindings. The server also writes every edit to it, the whole file in one layout. `Agreement` says where they and the rules disagree, every specification held to every rule set, a binding naming its rule set as `signup#/inputs/book` where there is more than one — a binding to a rule the rules lack, a rule no element asks for, what the machine refers to and does not have — so the server keeps no state for it; the extension marks the answer as problems on both. With a check on its command line the server is that command line instead — `Command`'s `check`, `agree` and `replay`, told which rule set with `--rules` where there is more than one, run in an application's folder, the last one `Replay` on the application as built, headless — so what an agent runs is the program the editor runs. `show` is the same program drawing a situation of the test design for the extension's **Test cases**, each move said as the application's window says it — the words of the control `Reach.Say` finds for it, and the value entered beside it: `Replay.Stand` presses the route to it on the application as built, and the window is captured before each press, where it stands, and after each refusal there is pressed — the application drawing itself, never a picture drawn here — with all the design records at it beside, the values somebody chose to try there among it. `design` is the same program drawing the screen while it is designed, for as long as it is asked: `Designer` loads `MainWindow.axaml` as it is written now with Avalonia's runtime XAML loader — the application's assembly and what its build wrote beside it read into memory, so the application can be built again meanwhile — draws it with Skia, says where a point falls by where each control is laid out, lists as the controls to place every control those assemblies hold that can be made with nothing — no list of them is written anywhere —, puts one in a panel, among the items written in a list — a tab control's tabs — or in a part of a control drawn by a template of its own — a split view's pane, a tab's header —, written as a property element, none named anywhere, and shows a tab chosen on the window it draws and never in the text, and writes each change, a control placed, moved, sized, deleted or given its words, as the smallest edit to the text — where it is, in a grid, as its margin from the top left of its cell, the way Visual Studio's WPF designer writes it, and an empty window given a grid where a control is dropped on it —, or a property given: every property Avalonia registers for the control's type and the attached ones of what holds it, that XAML writes as text, listed with the kind of value each takes, none named anywhere, which `Markup` reads as XML and nothing more. A choice is written into the design's `edits` by the server's `Choice`, the one place Ruledger's form of one is written, and the extension derives the design again; nothing of it is kept in the extension. What a change to the rules did is Ruledger's account and is never worked out here from two designs: the server takes the `Ruledger` package, and `Changes` asks it to apply the design the rule set as last committed gives — derived again from those rules, carrying the choices of the design committed with them — to the rules as saved and says each situation it names by the moves that reach it — `changes` on the command line — and the extension stands the window there before and after, each the application built from what it was written in, as last committed and as saved now, by `git archive` into a folder of its own, never the folder's own build. A change the person wants is asked of whatever agent they use, in its own place: the extension writes nothing down for an agent and starts none. Before there are any rules there is no situation to look at: the person writes the screen and the specification of a folder **New application** made. The rules are then written by that agent. What changed of the specification and the screen beyond binding them to the rules, against what was last committed, is the server's `Beyond`, which reads elements and XAML as names and nothing more; the view says it under the screen and the specification wherever either differs from that commit. Committing, putting a folder back and making a repository are git's, done in VS Code's Source Control or by the person's agent; the extension does none of them, and reads git only for a file as last committed. A refusal is said in the label document beside the rule set, read from the folder and never out of the application, and `replay` holds the screen to the same sentence. Everything the person does starts from the extension's own view in the activity bar, `view.ts`: with no application, VS Code draws the manifest's welcome there — making one, the example, the walkthrough; with one, it is the application under its folder's name — its screens, its specifications and its **Test cases**, each kind under a line of its own whose + adds one, each file called by its name so that VS Code's own find on the view, from the magnifier above it, finds one among many, each window and specification deleted from its own line, into the trash, the last window never, and the test cases one line for each rule set, by its name, each a page of two tabs: the test cases, fewest steps first, each its steps on the window and its expected result, narrowed by a search and by what they are — a chosen value's, a refusal, an ending — under the test cases the change since the last commit changed, added or removed, which head the list; and the values chosen to try, added and listed there, each said by what the screen calls the box it is entered in — `Captions` in the server, which reads from the XAML the box's own AutomationProperties.Name, or the nearest words written before it out to three levels of what holds it and never another box's, and is the only place that rule is written; where it finds none the value is said by its name in the rules, as that. The walkthrough is a view of its own below it. It opens things and draws nothing again. A rule set is the agent's to write and opens as the JSON it is; the extension has no editor for it, since nobody the view is for reads one, and the Problems panel says where it does not compile. Nothing in TypeScript reads a rule — a guard evaluated there would be a second account of the rules; the one thing it reads of a rule set is its `$schema`, to tell it from other JSON. A specification opens in the extension's custom editor, `Specification`, which draws what the server read of it as the diagram, sentences and a table, and edits it by asking the server for the whole text after an edit; it reads no meaning out of an element. A window opens in the other, `Screen` (`screen.ts`): the window `design` drew, the controls to place and what is placed, each change put in place as the one span of text the designer's answer differs in and saved, and the window drawn again whenever the text changes, whoever changed it. Nothing placed there is bound, and nothing in TypeScript reads XAML. Where the application was never built, it is built in a folder of the editor's own, so that the folder's first build is the one made with its rules; where it was, and what it is built from was written since — by an agent that did not build it, or a build that failed — it is built again before it is drawn, as **Test cases** builds it again before they are listed, and shown as last built where it does not build as written, which both say above everything, with when it was last built and what the build said, until it builds.

The extension, RulealizeStudio.Avalonia, reaches somebody as one `.vsix`, which `npm run package` writes with the server, the feed and the walkthrough's example — countdown, made into an application by the template — inside it. The extension's `installed.ts` is where every program it runs comes from: a .NET runtime on the machine or acquired by the .NET Install Tool, the SDK and the pinned `ruledger` and `rulealize` fetched only after asking, and a setting naming any of them still winning. Run from this repository, it takes the server and `feed/` built here instead.

## Testing
Headless Avalonia drives the real window — filling an editor, pressing a button, reading what landed under a field. A test that asserts a control exists is worth little; one that asserts the control came out of the runtime's answer is the point.

The vocabularies the test documents require are ordinary package references, so the sweep is pointed at the test project's own output folder.
